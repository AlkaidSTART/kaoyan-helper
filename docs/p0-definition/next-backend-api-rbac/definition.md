# P0 - Next.js 后端接口与 RBAC 需求定义

> 版本：v1.0  
> 日期：2026-09-26  
> 状态：接口与权限设计基线，待实施验证

## 1. 背景

当前 Flutter 客户端直接依赖 `supabase_flutter` 访问 Supabase Auth、PostgREST 与 Edge Functions；Next.js 仅作为管理后台。该方案在 MVP 早期可以快速验证，但随着题目判分、错题状态、SM-2 复习、UGC 审核、AI 配额和管理操作增多，业务规则会散落到客户端、数据库策略和多个 Edge Function 中。

本次架构调整的目标是：

- Flutter 的业务请求统一调用 Next.js 提供的 HTTP API。
- Next.js 作为 Flutter 与管理后台共用的 BFF/API 层。
- Supabase 继续负责 Auth、PostgreSQL、Storage 等服务。
- 管理员与普通用户的权限由服务端根据 RBAC 强制判定。
- Flutter 不再直接访问业务数据表，不再自行判题或修改受保护的学习数据。

## 2. 目标用户与系统角色

| 角色 | 说明 | 主要能力 |
|---|---|---|
| 游客 | 未登录用户 | 仅访问登录、验证码发送、健康检查等公开接口 |
| 普通用户 `user` | 已登录考生 | 管理个人资料、刷题、错题、目标院校、闪卡复习、AI 答疑 |
| 管理员 `admin` | 运营或内容管理人员 | 普通用户能力，以及后台看板、用户封禁、题库与院校数据维护、UGC 审核 |
| Flutter 客户端 | 原生/桌面/Web 客户端 | 仅通过 Next.js `/api/v1` 访问业务能力 |
| Next.js BFF | API 与管理后台载体 | 身份验证、参数校验、RBAC、业务编排、响应标准化 |
| Supabase | 数据与身份平台 | Auth、PostgreSQL、Storage、RLS |

## 3. 实际问题

### 3.1 客户端职责过重

- 判题、错题连对次数、掌握状态等规则若保留在 Flutter，容易出现版本差异和数据伪造。
- Supabase 表结构直接暴露给客户端，接口变更会同时影响 Dart DTO、SQL 与 RLS。
- Flutter Web、移动端、桌面端难以统一处理服务端错误与限流。

### 3.2 权限规则不集中

- `admin` 判断目前需要到管理后台自行实现，Flutter 与 Next.js 没有统一契约。
- 管理员绕过 RLS 使用 `service_role` 时，如果路由权限检查遗漏，会形成高权限数据泄露风险。
- 普通用户接口需要同时保证“已登录”和“只能操作自己的数据”，仅检查角色并不充分。

### 3.3 接口缺少统一标准

- 成功、失败、分页、时间、请求追踪和异常码没有统一结构。
- 401 与 403 的业务含义容易被客户端混淆。
- AI SSE、批量导入、幂等写入等接口需要明确的单独协议。

### 3.4 现有文档与目标架构冲突

当前 `prd-mvp.md` 与 `tech-stack.md` 中的 v3.0 基线仍描述 Flutter 直连 PostgREST。新接口方案必须先形成独立基线，待实现并验证后再统一迁移全局文档。

## 4. 目标

### 4.1 业务目标

1. 建立 Flutter 与 Next.js 之间可长期演进的 `/api/v1` 接口契约。
2. 建立 `user` 与 `admin` 两级 RBAC，并支持细粒度权限和资源所有权检查。
3. 将判题、错题更新、闪卡间隔计算、UGC 审核、用户封禁等关键规则收敛到服务端。
4. 保证管理后台与 Flutter 可复用同一套身份、权限和领域服务。

### 4.2 技术目标

1. Flutter 业务层只依赖 Repository 与 Next.js API，不直接调用 Supabase 数据表。
2. Next.js 统一输出成功、错误、分页、请求 ID 等响应结构。
3. 普通用户请求保留 RLS 作为纵深防御；管理员高权限操作必须经过显式 RBAC 检查。
4. 所有敏感密钥只存在服务端环境变量中。
5. 接口设计支持 Flutter 多端、Web 管理后台和后续服务拆分。

## 5. 范围

### 5.1 本期范围内

- `/api/v1` 版本与命名规范。
- 认证、用户、仪表盘、题库、错题、院校、闪卡、打卡、AI 与管理端接口目录。
- 请求/响应 DTO、统一错误结构、分页和 SSE 协议。
- `user` / `admin` 角色、权限矩阵、路由与所有权校验规则。
- Flutter Dio/Repository/状态层改造边界。
- Next.js 路由、服务层、RBAC、Supabase 客户端分层。
- 接口测试、权限测试和迁移验收清单。

### 5.2 本期范围外

- 本阶段不直接实现 API 路由和 Flutter 网络层代码。
- 不新增支付、社交、推送、短信登录或复杂运营后台。
- 不改变已有产品的核心学习流程。
- 不把 Next.js 管理后台的完整 UI 纳入本次接口文档。
- 暂不开放管理员角色授予 API；管理员仍由受控数据库操作产生。

## 6. 关键假设

1. Supabase Auth 继续作为身份提供方。
2. `public.users.role` 是角色唯一事实源，取值仅允许 `user`、`admin`。
3. Flutter 使用 Bearer Token；管理后台浏览器使用 HttpOnly 会话 Cookie。
4. Next.js 可同时承载管理后台页面与 `/api/v1` Route Handlers。
5. 普通用户业务请求优先携带用户 JWT 访问 Supabase，以保留 RLS 纵深防御。
6. 管理员操作使用仅服务端可用的高权限客户端，但必须先通过 RBAC 与业务校验。
7. 生产环境全链路 HTTPS，所有时间使用 UTC RFC3339 格式。

## 7. 用户场景

### 7.1 普通用户

1. 用户通过邮箱验证码完成登录，获得访问令牌、刷新令牌、角色与权限列表。
2. 用户获取题目列表，题目响应不包含标准答案和解析。
3. 用户提交答案，由 Next.js 判分并更新错题状态；客户端只展示结果。
4. 用户查询和管理自己的目标院校。
5. 用户获取到期闪卡并提交评级，服务端计算 SM-2 结果与打卡状态。
6. 用户使用 AI 答疑，服务端根据用户身份执行每日配额限制。

### 7.2 管理员

1. 管理员通过管理后台登录，服务端签发 HttpOnly Cookie。
2. 访问 `/api/v1/admin/*` 时，服务端校验登录态、`admin` 角色和具体权限。
3. 管理员可查看统计、封禁用户、维护题库与院校数据、审核 UGC。
4. 权限不足时返回 403；未登录时返回 401。
5. 所有高风险写操作必须记录操作者、目标对象、动作和请求 ID。

## 8. 验收指标

| 指标 | 验收标准 |
|---|---|
| 接口覆盖率 | 已定义的 MVP 功能均有明确 Method、Path、鉴权、请求、响应和错误码 |
| RBAC 完整性 | 每个受保护接口都声明所需权限、资源范围或所有权规则 |
| 权限隔离 | 普通用户无法访问 `/api/v1/admin/*`，无法读取或修改其他用户私有数据 |
| 客户端安全 | Flutter 不持有 `service_role`、DeepSeek Key 等敏感凭证 |
| 错误一致性 | 401、403、404、409、422、429、5xx 均有稳定业务错误码 |
| 判题可信 | 普通题目响应默认不返回答案，判题与错题更新由服务端完成 |
| 可追踪性 | 每个响应包含 `requestId` 与 UTC 时间戳 |
| 可测试性 | 所有权限分支、所有权分支和关键业务分支均进入 P3 测试矩阵 |

## 9. 风险与约束

| 风险 | 影响 | 应对 |
|---|---|---|
| 管理后台高权限客户端绕过 RLS | 授权遗漏会扩大数据泄露范围 | 强制 `requirePermission`、最小化 service role 使用、增加审计日志 |
| 角色缓存过期 | 管理员被降权后仍可短时操作 | MVP 不做角色缓存；确有性能瓶颈时缓存不超过 60 秒并提供失效机制 |
| Flutter 迁移期间双通道 | 数据一致性难以保证 | 按模块迁移，迁移完成后业务数据只允许走 Next.js |
| OAuth 经 BFF 改造复杂 | 移动端回调链路易出错 | MVP 先保证邮箱验证码；OAuth 单独设计一次性 handoff code |
| 接口目录过大 | 实现周期和契约维护成本增加 | 分为基础期、核心学习期、后台期，按 P2 依赖顺序交付 |

## 10. 决策结论

1. 采用 Next.js 作为统一 BFF，API 前缀固定为 `/api/v1`。
2. Supabase 不再是 Flutter 的业务 API 入口，只保留为身份、数据库和存储底座。
3. RBAC 必须同时在路由层和领域服务层执行；客户端角色仅用于 UI 展示。
4. 管理员权限采用“角色 + 权限 + 资源范围”模型，不使用单一 `isAdmin` 布尔判断。
5. 本文件只定义需求与验收边界，详细协议见 `docs/p1-design/next-backend-api-rbac/`。
